Plugin interfaces

How to add fuzzers, benchmarks, configuration generators, triage tools and post-analysis tools. Every plugin is a folder in the repository; the framework finds it by its folder name, so nothing else has to be registered unless a section says so. The repository's docs/CONTRIBUTING.md covers benchmarks and fuzzers in more detail, with complete sample files.

How the pieces fit

An experiment runs every fuzzer on every benchmark, under every compile-time strategy (which builds of the benchmark) and runtime strategy (which command lines it is fuzzed with). Everything runs in Docker:

  1. fbpp/base (from docker/base-image) is the parent of every image.
  2. Each fuzzer is built once as fbpp/fuzzer:<fuzzer>; running it copies the fuzzer into <experiment>/fuzzers/<fuzzer>/.
  3. A compile-time strategy turns benchmarks/<benchmark> into one or more copies benchmarks/cts_<strategy>_<benchmark>_<i>, each with its own build.sh.
  4. Each copy is built once per fuzzer (on top of fbpp/fuzzer:<fuzzer>, with the fuzzer's compiler) and once for coverage (with clang source-based coverage), into <experiment>/benchmarks/<fuzzer>_cts_… and …/coverage_cts_….
  5. Each trial runs the fuzzer's run.sh in fbpp/runner, then its coverage.py in fbpp/runner-coverage; output goes to <experiment>/data/<fuzzer>[_rts_<strategy>]_cts_…_trial_<k>/.
  6. After all trials: aggregation, SuperC (unless turned off), crash triage (if asked for) and the statistics report. Both combine each arm's trials two ways, always: the union (what any trial covered) and the mean over the trials (what a typical trial covers). The statistics report links a combined coverage report of each arm in both forms, with per source line how many trials covered it; SuperC's tables give each arm's conditions covered by the union, the mean trial and every trial.
Images are reused. When fbpp/fuzzer:<name>, fbpp/bug-triaging:<name> or fbpp/superc_runner already exists, it is not rebuilt. After changing a fuzzer, triage tool or SuperC, remove the image first, for example docker rmi fbpp/fuzzer:aflplusplus. Benchmark images are always rebuilt.

Adding a fuzzer

Folder: fuzzers/<name>/. The name is what you pass to --fuzzers or list in an experiment file. A fuzzer is one of two kinds:

Config-agnosticConfig-aware
What it fuzzesthe input file, under the command line it is giventhe input and the program's options, which it chooses itself
Hereaflplusplus, libaflvafuzz, configfuzz, carpetfuzz, prophetfuzz, zigzagfuzz
Runtime strategiesyes: each gives it a list of configurations, fuzzed one after anotherno: it always runs with default
Compile-time strategiesyesyes
Registered inruntime/supported_fuzzers.json, and run.sh reads ${SEED_DIR:-/benchmark/seed}fuzzers/benchmark_requirements.json, for the benchmark files it reads

Both kinds have the same three files:

FileRequiredWhat it does
builder.DockerfileyesBuilds the fuzzer image fbpp/fuzzer:<name>.
run.shyesFuzzes one trial.
coverage.pyyesReplays the trial's corpus on the coverage build and writes the coverage reports.

builder.Dockerfile

ARG parent_image          # the framework passes fbpp/base
FROM $parent_image

RUN git clone https://github.com/<you>/<fuzzer> /<name> && cd /<name> && make

# Compilers the benchmarks are built with (see below)
ENV FUZZER_COMP=/<name>/afl-clang-fast
ENV FUZZER_COMPXX=/<name>/afl-clang-fast++

COPY run.sh /<name>
COPY coverage.py /<name>
CMD ["bash", "-c", "cp -r /<name> /fuzzer_output/"]
  • Install into /<name>, with run.sh and coverage.py inside it. The framework runs the image once with <experiment>/fuzzers mounted at /fuzzer_output; the CMD copies /<name> there, and that folder is mounted at /fuzzer in every trial. (Only the first command of an exec-form CMD runs; the existing fuzzers' extra "&&", "cp …" items do nothing, which is why the files must be inside /<name>.)
  • Every ENV FUZZER_* is read from the image and passed to the benchmark builds as a --build-arg. Benchmarks use FUZZER_COMP and FUZZER_COMPXX as CC and CXX.

run.sh

Runs in fbpp/runner, pinned to two cores, with the memory limit from config.yaml.

GivenValue
/fuzzerthe folder your image copied out
/benchmarkthe benchmark built with your compiler: the binary, run_target.sh, seed/, dict, grammars, …
$OUT/fuzzer_output, the trial's folder (write everything here)
$RUNTIMEseconds to fuzz (the trial's time divided by the number of compile-time copies); 0 in continuous mode: fuzz until the container is stopped
$RUN_TARGETthe contents of /benchmark/run_target.sh, for example /benchmark/pcre2test @@; @@ is the input file
$SEED_DIRonly under a runtime strategy: the seeds to start from (the previous configuration's corpus)
 
# fuzzers/aflplusplus/run.sh (config-agnostic): fuzzes $RUN_TARGET as given, from $SEED_DIR
LIMIT=""; [ "${RUNTIME:-0}" -gt 0 ] 2>/dev/null && LIMIT="-V $RUNTIME"
export AFL_IGNORE_SEED_PROBLEMS=1
/fuzzer/afl-fuzz -i ${SEED_DIR:-/benchmark/seed} -o $OUT $LIMIT $RUN_TARGET

# fuzzers/zigzagfuzz/run.sh (config-aware): mutates the options with the benchmark's dict
LIMIT=""; [ "${RUNTIME:-0}" -gt 0 ] 2>/dev/null && LIMIT="-V $RUNTIME"
/fuzzer/afl-fuzz -i /benchmark/seed -o $OUT -K 2 -a /benchmark/dict $LIMIT $RUN_TARGET
  • Stop after $RUNTIME seconds. The container is killed after $RUNTIME + 600 s and the trial counts as failed.
  • When $RUNTIME is 0 or unset, run without a time limit (continuous mode stops the container itself), as the LIMIT line above does; anything else derived from the time (carpetfuzz's ranking budget) needs a fixed value then. In continuous mode the repository's run.sh is mounted over the one in the fuzzer image, so this works without rebuilding the image, and AFL_NO_AFFINITY=1 is set because Docker already pins the container to its CPU.
  • Write the corpus to $OUT/default/queue/ and crashes to $OUT/default/crashes/ (AFL++'s layout), which coverage.py and crash triage read.
  • A config-aware fuzzer that changes the command line saves it for each input and crash (as default/queue_argvs/ and default/crashes_argvs/ in vafuzz and zigzagfuzz), so that coverage and triage replay them with the same options.
  • A config-agnostic fuzzer takes its seeds from ${SEED_DIR:-/benchmark/seed} and is added to runtime/supported_fuzzers.json (below). Under a runtime strategy, runtime/multi_config_run.sh calls its run.sh once per configuration, with $OUT set to $OUT/config_<i>, $RUNTIME to that configuration's share and $RUN_TARGET to the program with the configuration's options, so run.sh needs nothing else for it.

coverage.py

Runs in fbpp/runner-coverage after fuzzing, with /benchmark now the coverage build of the same benchmark copy, /fuzzer_output the trial's folder, and $OUT and $RUN_TARGET as above. It must:

  1. run $RUN_TARGET on every corpus input (replace @@ with the input's path, or pass it on stdin) with LLVM_PROFILE_FILE set, each with a timeout;
  2. merge the profiles: llvm-profdata merge -sparse --failure-mode=warn -f inputs.txt -o $OUT/coverage/merged.profdata. Pass the profiles in a file list, one 1,<path> per line: a large queue exceeds the kernel's argument limit, and the explicit weight keeps the commas in AFL queue names from being read as one. --failure-mode=warn skips a truncated profile (a target killed while writing it) instead of failing the whole merge; list only profiles that exist, since a missing one fails it even then;
  3. write $OUT/coverage/report.json with llvm-cov export <binary> -instr-profile=… -format=lcov (LCOV, despite the name) and $OUT/coverage/report.txt with llvm-cov report <binary> -instr-profile=…. The binary is the first word of $RUN_TARGET.

The statistics report reads both files, aggregation copies report.json to lcov_results/, and SuperC reads that copy. Start from fuzzers/aflplusplus/coverage.py; if your fuzzer changes the command line per input (as zigzagfuzz and vafuzz do), replay each input with the arguments it was found with.

Continuous mode runs the same coverage.py on part of the corpus. Every round, runtime/continuous_coverage.py copies only the inputs found since the last round into a scratch $OUT ($OUT/default/queue/), together with default/queue_argvs/ and the regular files at the top of the trial's output (such as carpetfuzz's ranked_stubs.txt), runs coverage.py on it and merges its merged.profdata into the trial's cumulative profile. So coverage.py must work on any subset of the queue, and must read nothing else from $OUT than those; a fuzzer that needs another side file must add its folder to SIDE_DIRS in that script.

The coverage image is kept after the build: SuperC and the HTML source reports copy the sources out of it.

build.sh and run_target.sh

# build.sh: {{CT_CONFIGURATION}} is replaced by the compile-time strategy's options ("" for default)
./configure --disable-shared --enable-static {{CT_CONFIGURATION}} CC=$CC CXX=$CXX
make CC=$CC CXX=$CXX

# run_target.sh: one line; @@ is the input file
/benchmark/pcre2test @@

Build a static binary (or copy its libraries) so it runs from /benchmark.

ct_grammar.json: the compile-time options

{
  "name": "pcre2_pcre2test",
  "options": [
    {"name": "jit",  "type": "bool",   "default": false, "cli": "enable"},
    {"name": "link-size", "type": "choice", "default": 2, "cli": "with", "choices": [2, 3, 4]}
  ],
  "constraints": [
    {"opt": "jit-sealloc", "val": true, "then": [{"opt": "jit", "val": true}],
     "desc": "JIT Sealloc requires JIT to be enabled"}
  ],
  "removed": [{"name": "Werror", "reason": "compiler warnings would fail the build"}]
}

cli gives the configure flag form: enable gives --enable-x / --disable-x (or --enable-x=value for a choice), with gives --with-x / --without-x (or --with-x=value). constraints say which values imply others; strategies only produce configurations that satisfy them. removed documents options deliberately left out.

rt_grammar.json: the command-line options

{
  "cmdline": "$inopts $INPUTFILE",
  "options": [
    {"opt": "-i", "type": "bool"},
    {"opt": "--color", "type": "choice", "choices": ["always", "auto", "never"], "connector": "="},
    {"opt": "-S", "type": "intnum", "range": [1, 64]}
  ],
  "exit_options": ["-help", "-v"],
  "conflict": [["-t", "-T"]],
  "depend": [],
  "maxcombs": 2
}

Types: bool, choice (with choices), intnum and realnum (with range: the bounds and 8 values between are sampled), string (not sampled). $inopts is replaced by a configuration's options and $INPUTFILE by @@. exit_options make the target exit without reading its input and are never sampled; conflict pairs never appear together.

Adding a compile-time configuration generator

Folder: compiletime/<name>/strategy.py, selected with --compiletime <name> or compiletime: in an experiment file. A folder without strategy.py is not a strategy.

def request_configurations(grammar_file, random_seed=None):
    """grammar_file: path to benchmarks/<benchmark>/ct_grammar.json.
    Returns one string per build: the configure options that replace
    {{CT_CONFIGURATION}} in build.sh."""
    return ["--enable-jit", "--disable-jit --enable-unicode"]
  • Each string is one benchmark copy, benchmarks/cts_<name>_<benchmark>_<i>, built for every fuzzer and for coverage. compiletime/default returns [""]: one unchanged build.
  • A trial fuzzes every copy, with the trial's time split equally between them, so 20 configurations give each 1/20 of max_total_time. The statistics combine a trial's copies by the union of their covered lines and branches.
  • Be deterministic for a given random_seed (from config.yaml): the dry run calls the function to count copies and must get the same number as the real run.
  • Respect the grammar's constraints. compiletime/minimum/strategy.py has holds() and enforce() helpers for them.
  • An exception is caught and gives no configurations, so no copies and no trials for that benchmark: check the log for Failed retrieving configurations.

Adding a runtime configuration generator

Folder: runtime/<name>/strategy.py, selected with --runtime-strategy <name> or runtime_strategy: in an experiment file. Only fuzzers in runtime/supported_fuzzers.json and benchmarks with rt_grammar.json can use it.

import os, sys
sys.path.insert(0, os.path.dirname(os.path.dirname(os.path.abspath(__file__))))
from rt_common import Grammar, distinct

def request_configurations(grammar, rng):
    """grammar: the benchmark's rt_grammar.json, parsed.
    rng: a random.Random to use for all randomness.
    Returns a list of configurations, each a list of command-line arguments."""
    g = Grammar(grammar, rng)
    configs = distinct([g.random_config() for _ in range(100)])
    return [g.args(c) for c in configs if g.valid(c)][:20]
  • runtime/rt_common.py does the grammar work: Grammar.random_config() samples a valid configuration, valid(config) checks conflicts and dependencies, args(config) turns it into arguments following cmdline, and distinct() removes duplicates. Its docstring gives the sampling rules (from ConfigFuzz and VAFuzz).
  • Use only rng. The framework seeds it from the experiment's random_seed, the strategy, the benchmark and the trial, so every trial gets its own configurations and a rerun gets the same ones. It then shuffles the list and writes <experiment>/rt_configs/<name>/<benchmark>/trial_<k>.json.
  • How they are fuzzed (runtime/multi_config_run.sh): one after another, at most RUNTIME / min_config_time of them (60 s by default, min_config_time in config.yaml), each getting an equal share of the time left and starting from the previous configuration's corpus. The framework shuffles your list per trial, so when there are more configurations than fit, each trial fuzzes a different random subset.
  • Coverage (runtime/multi_config_coverage.sh): each configuration's new inputs are replayed with its own arguments and the profiles merged into the trial's report.
  • Return at least one configuration. Only the strategy named default runs the normal single command line (its request_configurations returns [] and is never called); any other strategy with an empty list leaves its trials with nothing to fuzz.

Adding a crash triage tool

Folder: bug-triaging/<name>/ with a Dockerfile, selected with --bug-triaging <name> or bug_triaging: in an experiment file. The image is fbpp/bug-triaging:<name>.

CMD ["python3", "/triage/triage.py"]
WhenGivenMust
after building, and before each experimentthe image, run with bash /smoke_test.shexit 0 when the tools work (for example, gdb loads its plugin)

  • /triaging_output is shared by all trials of a fuzzer under one runtime strategy on one benchmark copy (<experiment>/bug-triaging/<name>/output/<run label>_<copy>/), so add to it rather than overwrite it. Results are given to $OWNER, the user who started the experiment.
  • Replay each crash with the command line it was found with. bug-triaging/crash_commands.py finds it for every fuzzer (from run_target.sh, crashes_argvs/, the crash's name, or the runtime configuration it was found under); copy it into the image and use it.
  • For the statistics report's Found bugs table, write a SQLite database /triaging_output/crashes.db with a table Data that has a Hash column (the bug key), as afl-collect does. Distinct hashes are counted.

Adding a post-analysis tool

There are two kinds. A Python analysis reads the files an experiment leaves behind; this is how the statistics report works and is the simplest to add. A container analysis runs a tool in its own image, like SuperC; this is wired into the code rather than discovered from a folder.

What an experiment leaves behind

FileContents
<experiment>/experiment_state.pklthe plan: fuzzers, benchmarks, strategies, trial_tasks, paths, cores
<experiment>/events.jsonlphases and each trial's start, end, core and status
<experiment>/experiment.yamlthe experiment file it ran with
data/<trial>/trial_info.jsonfuzzer, runtime strategy, benchmark copy, trial number
data/<trial>/coverage/report.txtllvm-cov totals: regions, functions, lines, branches
data/<trial>/coverage/report.jsonLCOV: covered lines (DA) and branches (BRDA) per file

data/<trial>/default/the fuzzer's own output (queue, crashes); written by root in the container

A Python analysis

  1. Write common/<tool>.py with a function such as generate_<tool>_report(experiment_path, out_dir). common/statistical_analysis.py is the model: its load_trials() already reads every trial's coverage.
  2. Add a flag to common/post_analysis.py (next to --stats) that calls it with <report_filestore>/<experiment>/<tool>/, so it runs on finished experiments.
  3. To run it after every experiment, call it at the end of common/run_experiment.py, inside a try like the statistics, with events.emit(experiment_path, "phase", phase="<tool>") before it so the web app shows the phase.
  4. To offer it in the web app, add a checkbox to the Post-analysis tab (webapp/templates/experiment.html) and pass the flag in api_post (webapp/app.py).

A container analysis, like SuperC

SuperC (cfg-analysis/) finds the presence condition (#if condition) of every source line. common/superc.py runs it once per benchmark build and joins the conditions with every trial's coverage, giving coverage per condition in data/<trial>/pc_analysis/pc_coverage_summary.csv and the report in <report_filestore>/<experiment>/superc/. It is wired in like this:

SuperC's contract with benchmarks: superc_flags.txt lists the build's -I directories (relative to the source root) and -D defines, and the build runs in its source folder in the image, so the coverage report's paths point at the sources.

Testing a plugin

  1. Dry run. python3 common/run_experiment.py --config config.yaml --experiment exp.yaml --dry-run (or Preview in New experiment) checks that every name exists, every strategy has a strategy.py, and every fuzzer has the benchmark files it needs. It also calls compile-time strategies to count their copies.
  2. A short experiment: one fuzzer, one benchmark, one or two trials of 120 s. The experiment's page shows each trial's status and coverage, with a link to its log.
  3. Where to look when it fails:
    • fuzzer image: <experiment>/fuzzers/<fuzzer>_build.log
    • benchmark builds: <experiment>/benchmarks/<fuzzer>_<copy>_build.log
    • a trial's fuzzing and coverage: data/<trial>/<run>_<copy>_trial<k>.log
    • runtime configurations: data/<trial>/rt_run.jsonl and config_<i>/
    • triage: <experiment>/bug-triaging/<tool>/output/…/trial_<k>.log
    • SuperC: <experiment>/superc/<copy>/superc.log, a log per file in logs/, and status.tsv
  4. Coverage sanity check: a trial's coverage/report.txt should end with a TOTAL row whose covered branches equal the number of BRDA records with a non-zero count in report.json.
